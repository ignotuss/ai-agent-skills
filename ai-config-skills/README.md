# ai-config-skills

面向 AI 编码代理（Codex / Claude Code / Cursor / Copilot 等）的**配置表格维护与同步技能**集合。

一句话：让 AI 安全地改配置表——按需求改 xlsx、导出 JSON、同步到 Apollo 配置中心，并且**默认只停在草稿、绝不自动发布**。

## 这是什么

很多游戏/业务项目用**电子表格（xlsx）维护服务端配置**：表头固定几行，改完用工具导成 `ConfXxx.json`，再灌进配置中心（本项目适配 Apollo）。

这套流程本身不难，但容易出事故：

- 表改了没提交，仓库一更新改动就没了；
- 导出前忘了刷新暂存区，用的是旧副本，导出的 JSON 根本不是最新表；
- 表被 Excel 打开着，外部写入失败，或者用户一保存就把 AI 的修改覆盖回去；
- 有人直接在配置中心改了值、没回写表格，AI 再拿本地值一覆盖，线上配置就被顶掉了；
- 改的列其实是**客户端列**，服务端 JSON 里的内容一个字没变，用户却以为已经生效；
- 口头说的“发布”到底是“提交草稿”还是“让线上生效”。

本仓库把上述经验固化成**一个技能 + 一套守护工具**：让代理按固定流程走，并在每一步给出可核验的证据（哈希、读回比对、巡检报告）。

## 能做什么

| 能力 | 说明 |
| --- | --- |
| **改表** | 按自然语言需求定位到具体表/行/列并修改；改前输出“方案卡”待确认（跨表、删除、歧义场景必须确认） |
| **导出 JSON** | 表头 4 行规范，sheet 名 `中文\|English` → 产物 `Conf{English}.json`；导出前先把源表同步进暂存区 |
| **同步 Apollo** | 按 JSON 文件名匹配同名 `Conf*` 命名空间，OpenAPI 更新 `content` 键；找不到命名空间就停下反馈，不新建不改名 |
| **一致性校验** | 表间依赖检查（引用存在性、名称一致、时间顺序、枚举合法性……），规则按项目隔离 |
| **未提交改动守护** | 检查表改了有没有提交进配置仓库——未提交等于随时可能被覆盖丢失 |
| **漂移巡检** | 比对“表格里写的”与“配置中心里跑的”，逐命名空间列出差异 |
| **发布状态回填** | 用 `releases/latest` 自动判断草稿是否已发布，回填操作日志，不用再一条条问人 |
| **操作日志** | 每次任务一条 JSONL：需求、方案、改动、校验、导出哈希、同步状态、备份路径、遗留事项 |
| **Excel 占用预检** | 改表前检查 `~$` 锁文件，避免写入失败或“改了等于没改” |

## 工作原理

```text
自然语言需求
   │
   ├─ 第 0 步 需求分析与方案确认 ──► 输出“改哪张表、怎么改”的方案卡（等用户确认）
   │
   ├─ 第 1 步 改表 ──► 查依赖规则 → 预检 Excel 占用 → 改 → 读回校验
   │                   └─► 回报“本次改动落在服务端列还是客户端列”
   │
   ├─ 第 2 步 导出 ──► 源表同步进暂存区（只同步流水线内的表）→ 运行导出器 → Conf*.json
   │
   ├─ 第 3 步 同步 ──► 命名空间 = JSON 文件名 → OpenAPI 更新 content 键（POST 建键 / PUT 改键）
   │                   └─► 读回比对，确认与提交内容完全一致；默认停在草稿，不发布
   │
   └─ 收尾 ──► 提交表改动到配置仓库 → 写操作日志 → 跑漂移巡检
```

贯穿全程的三条原则：

1. **只提交、不发布**：配置中心里“保存条目”不等于生效，生效要靠显式发布。代理默认只更新条目。
2. **一切结论要有证据**：写入后读回比对、导出算 sha256、同步前先比对现状、巡检给出差异清单。
3. **知识按项目隔离**：不同项目的同名表可能语义完全不同，规则不跨项目套用。

## 安装

`SKILL.md` 就是“给代理看的指令文档”（Markdown + YAML frontmatter），所以**任何能读文件的代理都能用**。区别只在于该代理约定把这类文档放在哪里。

### 1. Codex

放进个人技能目录（Windows 即 `C:\Users\<你>\.agents\skills\`）：

```text
~/.agents/skills/ai-config-table-editor/
```

放好后新开一个会话，代理就能按技能描述自动匹配到它；也可以在会话里直接点名使用，或让代理用 skill-installer 从本仓库路径安装。

### 2. Claude Code

Claude Code 同样支持 Agent Skills（`SKILL.md` + frontmatter）。把整个技能目录放到技能目录下：

```text
~/.claude/skills/ai-config-table-editor/
```

目录名与 `SKILL.md` 里的 `name` 保持一致；`references/` 与 `scripts/` 要一起带上（技能文档会引用它们）。具体约定以 Claude Code 官方文档为准。

### 3. Cursor / Windsurf / 其它支持规则文件的代理

这类代理通常没有“技能目录”概念，但会读取项目级规则文件。把它们指向本技能即可：

```markdown
处理配置表格相关任务时，先阅读并遵循：
<技能目录>/ai-config-table-editor/SKILL.md
以及其 references/ 下的步骤说明与 table-knowledge/ 知识页。
```

放进 `.cursor/rules/` 或 `.windsurf/rules/` 下的规则文件里即可。

### 4. GitHub Copilot

在仓库的 `.github/copilot-instructions.md` 里引用同样的路径说明即可，写法与上一节一致。

### 5. 任意代理（通用兜底）

如果没有上述机制：

- **能挂载文件**：把 `SKILL.md` 的路径写进系统提示，要求代理“动手前先完整阅读该文件及其引用文档”；
- **不能挂载文件**：把 `SKILL.md` 内容直接粘进系统提示 / 自定义指令里（`references/` 内容较多，建议至少带上 step1~step3 与对应项目的知识页）。

## 使用方式

安装之后，用**自然语言**提需求即可，不需要记命令。以下是典型对话。

**① 改一个字段并同步**

> 商城表里“夏日海滩”那个商品改名成“夏日海岛”，然后同步一下。

代理会：确认唯一匹配的行 → 输出改动明细 → 改表 → 跑校验 → 导出 → 同步到对应命名空间草稿 → 报告差异与哈希 → 提示你去门户发布。

**② 跨多张表的改名**

> 把中秋牌背的名字统一改成“月满中秋”。

代理会：先全库检索这个名字出现在哪些表的哪些单元格 → 给你一张“待改清单”等你确认 → 确认后逐表修改 → 校验名称一致性规则 → 导出并同步涉及的所有命名空间。

**③ 活动配置**

> 中秋活动 9/24 16:00 开始，商店上架这几件商品，排行榜保留。

代理会：识别涉及活动表、活动商店表、道具表、Banner 表等 → 给出方案卡（含跨表联动与图片资源）→ 确认后执行。

**④ 例行核对**

> 跑一下漂移巡检，看看表格和 Apollo 有没有对不上的。

代理会：导出当前表 → 与配置中心逐命名空间比对 → 列出漂移项、待发布项，并说明每项的可能来源。

**⑤ 只是想看看**

> 这个值现在线上是多少？

代理只读查询，不做任何修改。

> 提示：如果代理判断改动跨表、涉及删除、或存在歧义，它会先给“方案卡”等你确认——这是设计如此，不是卡住了。

## 配置

通过环境变量注入运行参数，**令牌不要写进仓库**：

| 环境变量 | 说明 | 示例 |
| --- | --- | --- |
| `APOLLO_PORTAL_URL` | Apollo Portal / OpenAPI 根地址 | `http://apollo.example.com:8080` |
| `APOLLO_APP_ID` | 目标 AppId | `my-server` |
| `APOLLO_ENV` | 环境 | `DEV` |
| `APOLLO_CLUSTER` | 集群 | `default` |
| `APOLLO_OPERATOR` | 门户中的真实用户名（写条目的操作者字段） | `apollo` |
| `APOLLO_TOKEN` | 该 App 的 OpenAPI Token | 不提交 |

表格与导出目录按项目约定配置，文档中统一使用占位符：`$CONFIG_XLSX_DIR`（源表目录）、`$EXPORT_STAGING_DIR`（导出暂存区）、`$EXPORT_GEN_DIR`（导出器目录）。

## 核心约束

这些是硬性边界，代理会主动遵守并在报告里体现：

| 约束 | 原因 |
| --- | --- |
| **默认只提交草稿，不调用发布接口** | 配置生效影响线上，必须由人确认时机。只有用户明确说“真正发布 / 让配置生效”才允许调用 release |
| **不新建、不改名命名空间** | 命名空间被服务端配置引用，配置中心也不支持重命名；缺失时停下来反馈，由人处理 |
| **同步前先比对现状** | 本地的表可能落后于配置中心（有人直接在线上改过），盲目覆盖会顶掉线上配置 |
| **改表前检查文件占用** | 表被 Excel 打开时，外部写入会失败；更糟的是用户保存时用旧内容覆盖回去 |
| **改动必须提交进配置仓库** | 未提交的表改动会被子模块更新/拉取覆盖，真实丢过两次 |
| **必须回报“列去向”** | 客户端列的改动不会进服务端配置，不说明会让用户误以为已生效 |
| **知识按项目隔离** | 同名表在不同项目语义不同，套用规则会改错表 |
| **令牌从环境变量读取** | 不硬编码、不写入文档或日志 |

## 接入一个新项目

想让这套流程支持你自己的项目，按下面五步走：

1. **建知识页目录**：`references/table-knowledge/<项目名>/index.md`，用项目名做物理隔离。
2. **梳理表与依赖**：盘点表清单、字段语义、表间引用（谁引用谁）。**每条规则都要经人确认后才写入**，不要臆测。
3. **写项目校验脚本**：把已确认的规则实现成可执行检查，规则编号写在知识页里，脚本与知识页保持同步。
4. **定流水线清单**：列出哪些表参与导出与同步（子集通常比全部表小）。导出前只把这批表同步进暂存区。
5. **配环境变量**：配置中心地址、AppId、环境、集群、令牌。

建议一开始就把三样东西做出来：**一致性校验**、**未提交改动守护**、**漂移巡检**。它们对应的正是最容易出事故的三个环节。

## 常见问题

**Q：为什么代理不肯帮我直接发布？**
因为“改配置”和“让线上生效”是两件事。代理默认只把内容提交成草稿，发布由你在门户确认执行——这样你有机会检查差异再放行。若确实要代理发布，明确说“真正发布/调用发布接口”即可。

**Q：代理说找不到同名命名空间怎么办？**
它不会自动创建。请确认命名空间名字与 JSON 文件名是否一致，或在配置中心手工创建后重新同步。

**Q：表格和配置中心不一致，以哪边为准？**
先停下。两边各有可能是对的：线上可能被人手工改过，本地可能有未同步的新表。代理会列出差异让你决定方向，不会先斩后奏。

**Q：导出成功，但配置中心的内容没变化？**
大概率改的是**客户端列**（表头第 1 行标记为 `c`）。这类列不进服务端 JSON，需要走客户端配置渠道。代理应该在报告里说明这一点。

**Q：Excel 开着能改吗？**
不能。请先保存并关闭。存在 `~$` 锁文件时，外部写入会失败；就算写进去了，你之后在 Excel 里保存也会把修改覆盖掉。

**Q：本地表改了但没提交会怎样？**
有风险。配置仓库通常是独立子模块，一次拉取/还原就可能把未提交的改动覆盖掉。本技能内置了未提交改动检查，会在收尾时提醒。

**Q：这套东西和具体的配置中心绑定吗？**
核心流程（改表 → 导出 → 按名字匹配命名空间 → 更新条目 → 停在发布前）是通用的；具体接口适配在 `references/step3-apollo-openapi.md` 与 `scripts/update_namespace.ps1`，换配置中心时替换这一层即可。

**Q：知识库里的示例规则能直接用到我的项目吗？**
不能。`references/table-knowledge/` 里的内容是某个具体项目的真实规则（含字段陷阱与历史教训），用作**范式参考**；用在自己的项目上请按上一节重新梳理，或直接删掉该目录维护你自己的知识页。
